## 3. 실패 1 — `지형 파괴 후 넉백으로 맵 밖 → 낙사`

### 3-1. 테스트가 기대하는 것

`ScenarioAssetFactory.knockbackFall()`:

```
보스 Gate2 (0,0,0) · 슬레이어 1명 (0, 0, 23)  ← "외곽 벽 바깥 가장자리"
EnableFallDeath (지형 파괴 이후 상태, 바닥은 무너뜨리지 않음)
KnockbackMember: +z 방향 8m
기대: Died.Party = 1 (6초 안에)
```

설계 당시(외곽 벽 반지름 21m, 두께 1.2m) z=23 은 벽 바깥이었다. 8m 넉백 → z=31 은 바닥(반지름 26m) 밖 → 낙사.

### 3-2. 실제 결과

`Died.Party = 0` — 6초 안에 사망 없음.

### 3-3. 원인: 외곽 벽 위치 변경 (작업 트리의 콜로세움 작업)

커밋하지 않은 콜로세움 맵 작업이 `ArenaBuilder` 의 벽 치수를 바꿨다 (Meshy 콜로세움 맵 벽 안쪽 면에 맞춤).

| 값 | 커밋된 값 | 작업 트리 (현재) |
|---|---|---|
| `WallRingRadius` | 21.0 | **25.0** |
| `WallThickness` | 1.2 | **2.0** |
| `WallLength` | 5.4 | **6.8** |
| `CenterRadius` | 8.0 | 15.0 |
| 벽 바깥 면 | 21.6 m | **26.0 m = 바닥 반지름(26m) 과 같음** |

→ 현재 기하에서는 **"벽 바깥 바닥" 구간 자체가 없다**. z=23 은 벽 안쪽(안쪽 면 24m)이다.

넉백은 `ActorMotor.clipAgainstStructures` 가 0.25m 간격으로 서 있는 구조물과의 겹침을 검사해 그 앞까지 자른다.
현재 경기장 Prefab(같은 `ArenaBuilder` 코드로 구운 것)으로 같은 경로를 재현해 측정했다:

```
Wall_0 위치 (3.91, 1.75, 24.69) · 크기 (6.80, 3.50, 2.00) · Radius 1 · HalfLength 3.4
z=23 에서 +z 로 8m: 1.0m 지점에서 첫 벽 접촉 → 0.75m 로 잘림 → 착지 z=23.75
IsSolid(z=23.75) = True   (바닥 위)   · IsSolid(z=31) = False
```

+z 정면은 Wall_19(351°) 와 Wall_0(9°) 사이 틈(약 1m)이지만, 벽 판정이 캡슐(두께/2 = 1m 반지름)이라 끝부분이 둥글게 튀어나오고
캐릭터 반지름 0.45m 를 더하면 틈으로 빠져나갈 수 없다 (벽 끝점 (0.55, 25.22) 까지 거리 0.55m < 1.45m).
→ 착지점이 단단한 바닥이므로 `ArenaFloor.checkFalling` 이 낙하로 보지 않는다 → 사망 이벤트가 오지 않는다.

이번 작업과 무관함: 넉백 경로 · 낙사 판정 코드는 바뀌지 않았고, 경기장 Prefab 은 작업 트리의 `ArenaBuilder` 를 그대로 실행해 구운 것이라 예전 코드 조립 경로와 같은 기하다.

같은 계열의 다른 두 시나리오(`넉백 없이 바닥 밖 → 구출`, `지형 파괴 전 넉백 → 구출`)는 "죽지 않는다" 를 기대하므로 이 기하에서도 통과한다.

### 3-4. 고치는 방법 (결정 필요 — 콜로세움 기하 확정 뒤)

| 안 | 내용 | 비고 |
|---|---|---|
| A. 벽을 먼저 무너뜨린다 (권장) | 시나리오에 "구조물 전부 파괴" 단계(첫 즉사기 G2-03 과 같은 상태)를 넣고, 벽 안쪽(z=22 등)에서 바깥으로 8m 넉백 → 바닥 밖 | 실제 게임 흐름(즉사기로 벽 붕괴 → 지형 파괴 → 넉백 낙사)과 같다. 벽 치수가 다시 바뀌어도 깨지지 않게 위치를 `ArenaBuilder.WallRingRadius` 에서 계산 |
| B. 시작 위치만 옮긴다 | 벽 사이 틈 정중앙에서 넉백 | 현재 기하로는 캡슐 판정 때문에 틈을 못 지나감 → 불가 |
| C. 바닥을 무너뜨린다 | `Collapse` 로 외곽 타일을 무너뜨린 뒤 그 위로 넉백 | 지형 파괴 기믹 테스트와 겹침 |

설계 메모: 벽 바깥 면이 바닥 끝(26m)과 같아져서 **벽이 서 있는 동안은 넉백 낙사가 일어날 수 없다** — 의도한 규칙(지형 파괴 전에는 낙사 없음)과도 맞으므로 게임 규칙상 문제는 아니고, 테스트 전제만 갱신하면 된다.

## 4. 실패 2 — `밸런스 Gate1 15초`

### 4-1. 테스트가 기대하는 것

보스 Gate1(AI 끔) + 딜 측정기 4명(`ScenarioAutoAttacker`), 시간 배율 3, 시드 7, 15초 → 깎은 체력 줄 **−58 ~ −25** · 치명타 20 ~ 70%.
범위 주석: "현재 밸런스 측정값(15초 −48줄) 기준" (커밋 `42739e0`, 11-16).

### 4-2. 실제 결과

전체 실행에서 **−58.464** (상한 −58 을 0.46 줄 넘음). 치명타 42.4% 는 통과.

### 4-3. 원인 확인: 같은 시드로도 실행마다 값이 다르다

같은 테스트만 반복 실행 (Prefab 경로 3회 + Prefab 을 끈 예전 코드 조립 경로 3회 대조 실험):

| 실행 | 경로 | 체력 줄 변화 | 치명타 % | 타격 수 | 판정 |
|---|---|---|---|---|---|
| 전체 실행 | Prefab | −58.46 | 42.4 | 198 | 실패 |
| 1 | Prefab | −58.66 | 39.8 | 171 | 실패 |
| 2 | Prefab | −52.86 | 41.4 | 162 | 통과 |
| 3 | Prefab | −53.75 | 40.9 | 181 | 통과 |
| 4 | 코드 조립 (Prefab 끔) | −51.83 | 42.2 | 180 | 통과 |
| 5 | 코드 조립 (Prefab 끔) | **−60.00** | 45.6 | 180 | 실패 |
| 6 | 코드 조립 (Prefab 끔) | −48.71 | 40.9 | 176 | 통과 |

- 7회 평균 **약 −54.9 줄**, 범위 −48.7 ~ −60.0 (폭 약 11 줄). 7회 중 3회 실패.
- Prefab 을 끈 예전 경로에서도 실패(−60.0)하고 분포가 같다 → **월드 Prefab · Addressables 전환과 무관**. (대조 실험용 임시 코드는 측정 후 되돌림)

흔들리는 이유 (코드 확인):
- 딜 측정기는 `Update()` 마다 "시전 중이 아니면 다음 스킬" 을 고른다 → 15초(게임 시간) 안의 시전 횟수 · 순서가 **프레임 간격에 따라 달라진다** (시간 배율 3 이라 한 프레임이 게임 시간으로 길다).
- 치명타 · 피해 판정은 시드 고정 난수(`GameRandom`)를 쓰지만, 시전 순서가 달라지면 난수를 꺼내는 순서도 달라져 같은 시드라도 결과가 달라진다.
- 시나리오 끝(15초)도 프레임 단위로 잘려, 마지막 타격 하나가 들어오거나 빠질 수 있다 (타격 1회 ≈ 0.3 ~ 0.4 줄).

### 4-4. 측정값이 −48 에서 −55 쪽으로 옮겨간 것

범위를 정한 11-16 측정(−48 줄)보다 평균이 약 7 줄 크다. 그 뒤 전투 관련 변경은 `6704e06`(스킬 시전 애니메이션 · 시전 속도 반영), `f985604`(패턴 ID → ETag) 등이다.
다만 측정 한 번 값(−48)이 원래 분포(−48.7 ~ −60)의 아래쪽 끝이었을 가능성도 있어, **"밸런스가 바뀌었다" 고 단정할 근거는 아직 없다**. 한 번의 측정으로 범위를 정한 것이 근본 원인에 가깝다.

### 4-5. 고치는 방법 (결정 필요)

| 안 | 내용 | 비고 |
|---|---|---|
| A. 결정적으로 만든다 (권장) | 밸런스 시나리오만 고정 간격으로 진행 (`Time.captureDeltaTime` 또는 딜 측정기를 고정 틱으로) → 같은 시드 = 같은 결과 | 범위를 좁게 잡아도 깨지지 않고, 밸런스 변화가 생기면 정확히 드러난다 |
| B. 범위를 분포에 맞춘다 | 여러 번(예: 10회) 측정해 평균 ± 여유로 범위 재설정 (현재 분포면 예: −65 ~ −40) | 빠르지만 흔들림은 남는다 |
| C. 여러 번 돌려 평균으로 판정 | 같은 시나리오를 N 회 반복하고 평균만 검사 | 실행 시간 N 배 |
